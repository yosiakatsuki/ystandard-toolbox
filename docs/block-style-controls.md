# ブロック設定の共通設計

## 役割と適用範囲

Toolboxのブロック開発全般に適用する設定UIの設計を定める。設定の配置、WordPress標準機能の利用、共有パネル、ファイル構成、保存・更新・リセットを対象とし、レスポンシブ設定もこの設計の一部として扱う。

本書には特定のブロックの機能名・操作・パネル一覧・実装例・検証履歴を含めない。資料の役割は次のように分ける。

- 本書：ブロックを問わず適用する判断基準と実装規約
- 各ブロックの`DESIGN.md`：対象要素、採用する設定、固有の操作、保存先、既定値、適用優先順位、例外とその理由
- 共有コンポーネントの仕様：値の型、props、更新・解除時の契約
- 検証仕様と実行記録：確認項目、実行結果、未確認の範囲

新規ブロックと既存ブロックへ新しく追加する設定には本書を標準適用する。既存の未対応箇所は順次対応し、依頼範囲外を一括変更しない。未対応箇所は対象ブロックの`DESIGN.md`へ、現状・目標・互換性への影響・確認項目を残す。資料の更新だけで実装まで適合したものと扱わない。

以下のパスはプロジェクトルート基準とする。

## 設定を追加する前に決めること

設定ごとに、利用目的、対象要素、変更するプロパティ、保存先、既定値、許可する値・単位、適用優先順位、解除後の状態を決める。

既存の設定で目的を満たせる場合は、同じ対象・同じプロパティの入力を重複させない。共通設計を理由に、必要のない設定を各ブロックへ追加しない。

## 設定グループとスタイルグループの判断基準

### スタイルグループに置く設定

次のいずれかに該当するプロパティを設定するパネルは、`InspectorControls`の`group="styles"`へ置く。

- Block Supportsで追加できる色・文字・背景・枠線・余白・寸法などのスタイルプロパティと同じもの
- HTMLの`style`属性に指定できるCSSプロパティ。Block Supportsで直接提供されないものや、子要素へ適用するものも含む

判断の基準は、設定が制御するプロパティと適用対象とする。保存値がCSSカスタムプロパティ・プリセットトークン・クラスを経由して適用される場合も、制御対象がCSSプロパティならスタイル設定として扱う。通常値とレスポンシブ値で分類を変えない。

### 設定グループに置く設定

内容、参照データ、リンク先、取得条件、ブロック構造、機能の有効・無効、操作に伴う動作などは設定グループへ置く。Block Supportsの機能であっても、装飾のプロパティではないものまでスタイル設定とみなさない。

見た目に影響するという理由だけでスタイルグループへ入れない。CSSプロパティの編集と、内容・構造・動作を変更する機能を区別する。両方を含む操作や分類しにくい固有機能は、操作全体の目的と配置理由を各ブロックの`DESIGN.md`へ記載する。

### ブロックツールバーに置く設定

編集しながら頻繁に切り替える短い操作はツールバーへ置ける。WordPress標準の操作がある場合はそのパターンを優先し、詳細な数値入力はインスペクターへ置く。同じ値を複数箇所から操作する場合は、保存先・選択状態・解除処理をそろえ、重複配置の理由をブロック設計へ残す。

## WordPress標準機能の利用

- 要件と適用先を満たせる場合はBlock Supportsと標準UIを使う。同じ対象・同じプロパティの独自パネルを追加しない。
- Block Supportsで扱えない対象やプロパティには、共有パネルを使って独自UIを設ける。コアと同じ概念の設定は名称・入力・追加・解除の操作をそろえる。
- 標準機能の適用先を子要素へ変更する場合は、外側への自動出力と子要素への出力を二重にしない。編集画面・保存HTML・フロントで同じ要素へ適用する。
- コアが使うプリセット属性と保存形式は維持する。独自スタイルは`style.ystdtb.{ブロック固有キー}`配下で対象要素・用途ごとに整理する。
- 標準対応が要件に対して過剰になる場合は、代替案と判断理由をブロック設計へ記載する。

## パネルのaktk-component化

### 共有パネルを使う原則

独自に作成するパネルは`src/aktk-block-components/components/`でコンポーネント化し、ブロック側から利用する。初回利用でも、入力部品だけを共有してパネル全体をブロック内へ作り込む構成を基本にしない。Block Supportsが自動生成する標準パネルを独自コンポーネントへ作り直す必要はない。

既存の共有パネルを確認し、目的と契約が合うものを使う。該当するパネルがなければ、用途ごとに独立した共有パネルを作る。既存パネルへモードや機能切替を追加して、異なる用途を兼ねさせない。

### 共有パネルの責任

- パネルの見出し、項目、入力部品、追加メニュー、設定済みの判定、個別解除・全解除のUIを提供する。
- 受け取った値を表示し、そのパネルが扱う範囲の更新値・解除をコールバックで返す。
- ラベル、パネルID、値、更新関数、許可する辺・単位などを中立的なpropsとして受け取る。
- ブロック名、属性の保存パス、親子同期、コンテンツ取得、プラグイン固有のロゴを内部へ埋め込まない。

### ブロック側の責任

- パネルごとの独立したファイルで、属性から対象値を取り出し、共有パネルへ渡す。
- 返された値を、そのパネルの担当する保存先だけへ反映する。他の属性・要素・端末の値を保持する。
- `InspectorControls`への配置、翻訳したパネル名、パネルID、表示対象の有無、必要な親子同期を扱う。
- パネル固有の保存・適用・互換性の仕様を`DESIGN.md`へ記載する。

共有パネルを使うことと、ブロック固有の属性更新を共通ラッパーへ集約することは別に考える。

## ファイル分離と共通化の境界

### パネルごとの独立した入口

共有パネルは`src/aktk-block-components/components/{パネル名}/index.tsx`、ブロック側のスタイル設定は`inspector-controls/styles/{パネル名}/index.tsx`を入口にする。設定グループの独自パネルも`inspector-controls/{パネル名}/index.tsx`へ分ける。

paddingとmarginに個別のパネルを設ける場合は、共有パネル側・ブロック側ともそれぞれ独立したファイルにする。「レスポンシブ余白」にまとめる場合の項目構成は「レスポンシブ設定」に従う。通常設定とレスポンシブ設定、異なる対象要素のパネルも、ブロック側ではそれぞれの入口で値の取得・更新・解除を明示する。Block Supportsが自動生成するコアのパネルまで分割し直すことは求めない。

次は構成例であり、実在するコンポーネントの一覧ではない。

```text
src/aktk-block-components/components/
├── padding-panel/index.tsx
├── margin-panel/index.tsx
├── responsive-padding-panel/index.tsx
└── responsive-margin-panel/index.tsx

src/blocks/block-library/{block}/inspector-controls/styles/
├── padding/index.tsx
├── margin/index.tsx
├── responsive-padding/index.tsx
└── responsive-margin/index.tsx
```

### 共通化してよい範囲

`ToolsPanel`・`ToolsPanelItem`、入力部品、型、値の検証・変換、他の設定を保持する更新ユーティリティは共通化できる。同じ用途の共有パネルを複数のブロックや対象要素から使うこともできる。

一方、`mode`・`kind`・`element`などでパネルの用途、構成、保存先、解除範囲を切り替える共通ラッパーは作らない。入口ファイルだけを分け、その先でモードを渡して同じ処理へ戻す構成も採用しない。paddingとmarginをひとつのパネル実装で切り替えたり、ブロック内の異なる対象のパネルを対象名の引数で切り替えたりしない。

ラベル・パネルID・値の受け渡しや、同じプロパティに対する許可単位・対象辺の指定は、用途を切り替えるモードとは区別する。共有の余白入力を独立したpaddingパネルとmarginパネルの内部で利用することはできる。

## パネルの表示と命名

- スタイルの独自パネルは`ToolsPanel`・`ToolsPanelItem`による項目追加・個別解除・全解除を使う。共有パネル側でこの操作をそろえる。
- スタイルグループの入力項目はすべて初期非表示とする。独自項目は`isShownByDefault={ false }`、Block Supportsは`__experimentalDefaultControls`の対象項目を`false`にする。
- 初期非表示とは未設定の入力を出さない状態を指す。見出しと追加メニューは表示し、別のアコーディオンで囲まない。保存値がある項目は自動表示し、値を隠したり初期化したりしない。
- パネルは対象要素と用途で分ける。異なる役割の設定を総合パネルへ詰め込まず、同じ種類の設定は名称と相対的な順序をそろえる。標準パネルの配置はコアに従い、通常設定の後へレスポンシブ設定を置く。
- ysアイコンはレスポンシブ系のパネルだけに付ける。ブロック側から共有パネルへ渡し、通常のパネルや共有入力部品には付けない。
- 同じ見出しを二重表示しない。ラベル内包の入力部品を外側から同じラベルで囲まない。アクセシブルな入力名は残す。
- 説明文は設定の意味・単位・対象など、操作判断に必要な内容に絞る。

## 保存・更新・リセットの共通契約

- 更新はそのパネルの対象設定だけを変更し、他の要素・項目・属性を保持する。初期値を毎回上書きしない。
- 未設定、0、false、空文字列の意味は設定ごとに決める。有効な0やfalseを単なる未設定として消さない。
- 独自スタイルの解除は`undefined`で表現し、空階層は既存の`stripUndefined()`で除去する。コア属性の解除はコアの保存形式に従う。
- 個別解除は対象項目だけ、全解除はそのパネルの担当範囲だけに限定する。別パネルや子ブロックへ不要な変更を広げない。
- 一括適用・親子同期が必要な場合は、上書きする項目と保持する項目をブロック設計へ明記する。
- 保存形式・出力要素を変更する場合は、リリース済み形式との互換性を確認する。UIの移動と保存形式の変更を区別する。

## レスポンシブ設定

幅・最小幅・最大幅・高さ・最小高さ・最大高さの端末別入力は、スタイルタブの「レスポンシブサイズ」にまとめる。各ブロックが使用する寸法を指定し、有効な寸法ごとにパネル項目を1つ表示する。paddingとmarginは余白の設定として扱う。

共有の`ResponsiveSpacingPanel`は、現在「カラムの間隔」（gap）に対応している。将来、端末別のpadding（内側の余白）とmargin（外側の余白）も同じ「レスポンシブ余白」パネルに追加できるようにする。追加時はgap・padding・marginを独立したパネル項目にし、ブロックごとに使う項目を指定する。各項目の入力・保存・個別解除はそれぞれの設定に閉じ、全解除ではそのブロックで有効な端末別の余白だけを消す。

### 値と適用の契約

- 通常値と端末別値は併存する。端末別値があるプロパティだけを上書きし、未設定なら通常値または既定のスタイルへ戻す。
- `desktop`・`tablet`・`mobile`間で値を継承しない。他端末の値をフォールバックに使わない。
- 親から継承する設定がある場合は、子の端末別値・子の通常値・親からの継承の優先順位をブロック設計へ明記する。
- 通常入力の変更・解除は通常値だけ、端末別入力の変更・解除は対象端末の対象設定だけに限定する。
- レスポンシブパネルの個別解除・全解除では、その担当範囲の端末別値だけを削除し、通常値・他パネルを保持する。
- 通常設定とレスポンシブ設定は独立したパネル・ファイルで扱う。レスポンシブパネルに通常入力を混在させない。
- 端末別値は対象要素へCSSカスタムプロパティとして出力し、共通の`Styles`ヘルパーによる端末範囲を使う。編集画面とフロントで同じ要素へ適用し、ブレークポイントの数値を各ブロックへ複製しない。

### 検証パターン

レスポンシブ設定は、各プロパティについて次の5パターンで検証する。

- PCのみ
- タブレットのみ
- モバイルのみ
- PC・タブレット・モバイル全部指定
- タブレット・モバイルの2つ指定

端末ごとに異なる値を使い、指定端末での適用と未指定端末で通常値へ戻ることを確認する。辺別の余白は各辺を個別に照合する。通常値の保持、未指定端末のCSSカスタムプロパティを出力しないこと、保存・再読込も検証する。ブラウザ幅を変える確認は専用の新しいウィンドウで行う。

### 共有パネル内部で使う入力部品

- 端末別文字サイズ：`components/responsive-font-size-control`の`ResponsiveFontSizeControl`
- 端末別の辺別余白：`components/responsive-spacing-control`の`ResponsiveSpacingControl`
- 通常の辺別余白：`wp-controls/spacing-size-control`の`SpacingSizesControl`
- 単一の長さ：`wp-controls/unit-control`の`UnitControl`。端末別入力は`components/icon-control`の`IconUnitControl`を組み合わせる

これらは入力部品であり、パネルの共有コンポーネント化を置き換えるものではない。不足するパネルはaktk-component側へ追加し、ブロック側に入力の組み立てを複製しない。`@wordpress/components`を使う場合も既存の`wp-controls/`ラッパーを優先する。

部品は値の型、通常値との関係、返却値、解除範囲、ラベルの内包を確認して選ぶ。通常値と端末別値の変更時にもう一方を解除する切替型の入力は、両者を併存させる設定にそのまま使わない。既存部品の契約変更が必要なら、他の利用箇所への影響も確認する。

## 変更時の確認

- スタイルグループへの配置が、制御するプロパティを基準に説明できること
- 標準機能で対応できる範囲と共有パネルを使う範囲が明確で、同じ設定が重複しないこと
- 独自パネルがaktk-component化され、各ブロックの入口と属性更新がパネル単位で分離されていること
- 似たパネルの実装をモード切替へ集約せず、共通化が入力・型・ユーティリティまたは同じ用途の共有パネルにとどまること
- 初期表示、設定済みの表示、追加、入力変更、個別解除、全解除、通常値・他端末・他設定の保持を確認すること
- 共有パネルの値の契約と、ブロック側の保存先への反映を、それぞれ適切な範囲のテストで確認すること
- 保存HTMLを変更する場合はfixtureの入力・parse・移行後構造・再保存結果を確認し、ブロックの有効性と内容の保持も検証すること
- ブラウザ確認は許可範囲で行い、幅を変える場合は専用の新しいウィンドウを使うこと
- 特定ブロックの未対応箇所や検証結果を本書へ混ぜず、該当する設計・検証記録へ残すこと
